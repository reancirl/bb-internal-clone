# BuffaloBuilt Internal — Technical Audit

Audit date: 2026-09-05. Scope: full codebase at commit f6dafa0 (branch main). Read-only; no files were changed.

Stack at a glance: Laravel 12.61 (PHP 8.2), Inertia 2 + React 19 + TypeScript, Tailwind 4 + shadcn/Radix, Vite 6, Laravel Sanctum (mobile JSON API), DomPDF, Intervention Image. Local `.env` uses PostgreSQL; `.env.example` and CI use SQLite. Roughly 15.5K lines of PHP and 17.5K lines of TS/TSX, 33 feature test files with 260 test methods.

Legend used throughout: **Confirmed** = observed directly in code and reproducible from it. **Potential** = a risk that depends on data volume, deployment, or usage that the code alone cannot prove.

## 1. System Overview

### 1.1 What the system is

BuffaloBuilt Internal is an internal operations platform for a residential general contractor (BuffaloBuilt, Sheridan, Wyoming, per the PDF templates and seed data). It is a "Buildertrend-style" job-management tool built for two audiences: the **office** (estimating, sales, purchasing, budgeting, scheduling, reporting) and the **field crew** (clocking in, seeing their jobs, writing daily logs, capturing tasks and photos). A companion Expo/React Native mobile app consumes a token-authenticated JSON API for the crew-facing subset, and the public marketing website pushes leads in through one scoped API endpoint.

### 1.2 Business goals and problems solved

The seed data and docs show the app replacing a set of spreadsheets ("Material Master List", "Marys REVAMP" budget sheet) with a single system that:

- Captures website leads and works them through a sales pipeline to a won project.
- Turns a project's physical dimensions into material quantities via formulas (a takeoff), prices them from a shared price book, and freezes that estimate into a customer proposal PDF.
- Tracks the contract price plus approved change orders, and a bid-vs-actual budget per project.
- Requests and compares subcontractor quotes and writes the winning number straight into the budget.
- Issues purchase orders to suppliers from the takeoff and flips material status (ordered / on site) as POs move.
- Schedules jobs on a calendar with crew assignment and predecessor dependencies that shift downstream dates.
- Records field reality: daily logs with photos, a task and punch list with before/after photos, customer selections with allowances.
- Tracks hours for payroll via clock in/out and produces payroll and material-status reports.

### 1.4 Roles and permissions

There are exactly two roles stored in `users.role`: `admin` and `crew`. There are no per-object policies; authorization is role middleware plus a handful of ownership checks on models (`DailyLog::editableBy`, `ProjectTask::editableBy/workableBy`, job crew membership).

**Any signed-in user (crew and admin)**

- View dashboard (currently a placeholder), settings, own profile.
- Clock in / out (one open card at a time), view own time cards.
- Read-only: leads list, trade partners, vendors, price book, projects list and detail, takeoff CSV export, calendar, selections.
- Toggle any takeoff line's ordered / on-site flags.
- View and upload project photos (uploads attach to their own daily log for today).
- Create tasks on any project; edit/delete tasks they created; change status, tick checklist items, and add/delete photos on tasks assigned to them.
- Create daily logs; edit/delete their own logs and photos.
- See their own assigned jobs and change the status of jobs they are on.

**Admin only** (web `admin` middleware, `EnsureUserIsAdmin`)

- Create/update/delete trade partners, vendors, price items, projects, takeoff lines, jobs (plus dependency shift preview).
- Everything under `/admin`: CRM pipeline, analytics, lead CRUD and conversion, rates, employees (create, edit, reset password, deactivate/reactivate), decision catalog, proposals, sub bids, reports.
- Budget, change orders, contract price, purchase orders (all under `admin` in `routes/web.php`).
- Selections: generate, edit, choices, approve on behalf of the customer.
- Punch-list sign-off, and viewing other employees' time cards.

**API tokens (Sanctum)**

- Mobile token (`mobile` ability, issued by `POST /api/login`): user info, logout, time card, read directories and price book. Admin users additionally get write access to directories, price book, rates, and a stats endpoint.
- Website token (`leads:create` ability, created by the seeder for a service user): only `POST /api/leads`.

### 1.5 End-to-end workflow and data flow

1. **Lead intake.** The website POSTs to `/api/leads` with a scoped token. `Api\LeadController` stores a `Lead` (source `website`) and queues `LeadReceived` emails to opted-in admins. Office staff can also create leads manually on the kanban.
2. **Pipeline.** Admins drag leads across statuses (`new → contacted → qualified → meeting_scheduled → proposal_sent → won | lost`). Every status change writes a `LeadActivity`; moving to lost asks for a reason; won/lost stamp timestamps. Analytics is computed client-side from all leads.
3. **Conversion.** A won lead runs through a four-step wizard that creates a `Project` (optionally with all 15 dimensions, contract price, start date) and seeds the 13-line standard takeoff from `TakeoffTemplate`. The lead stores `converted_project_id`, so conversion is one-way and idempotent.
4. **Estimating.** On the project page, admins enter dimensions. Each `TakeoffLine` has a formula over dimension variables (`ext_wall_lft * 2 / 16`), waste percentage, optional price book link and supplier. `TakeoffCosting` evaluates quantity and cost server-side; `lib/formula.ts` mirrors the parser for live preview in the line dialog. The estimate roll-up groups cost by category and flags lines with quantity but no price.
5. **Proposal.** `ProposalController@store` snapshots every takeoff line into `project_proposal_lines` in integer cents with a per-year number (`PROP-2026-001`), then follows `draft → sent → accepted | rejected` (rejected can be re-sent). A DomPDF letter-size PDF is generated on demand.
6. **Contract and budget.** The project stores `contract_price_cents`. Change orders are numbered per project (`CO-n`) and, when approved, create a line in the budget's `CHANGE ORDERS` section. The budget itself is generated from a catalog (`budget_sections` / `budget_line_definitions`) into `project_budget_lines` with six money columns (sub bid/actual, material est/actual, labor est/actual). Variance = budgeted − actual.
7. **Sub bidding.** A `BidRequest` (draft → open → awarded | canceled) invites `TradePartner`s as `BidResponse` rows. Recording an amount flips a response to received. Awarding writes a `SUB BIDS` budget line with `bid_sub_cents` and locks the request.
8. **Purchasing.** POs (`PO-2026-001`) are built from takeoff lines or custom items, in cents. Transitions `draft → sent → confirmed → received` (or canceled). Sending marks linked takeoff lines ordered; receiving marks them on site. Committed cost = sum of sent/confirmed/received POs.
9. **Scheduling.** `ProjectJob`s have a start date, duration, trade, crew (pivot), and optional predecessor. Editing a job's dates on one with successors previews the downstream shift (`ScheduleShifter`) and optionally applies it to not-yet-started successors. Newly assigned crew get `JobAssigned` emails.
10. **Field execution.** Crew clock in/out (header button on every page). Daily logs record notes, weather, crew, issues, photos (resized to 1600px web + 400px thumb JPEGs on the private disk, streamed through auth-guarded routes). The project gallery is a read view over daily-log photos. Tasks capture punch items with checklists and before/after photos; when all punch items are done an admin records customer sign-off on the project.
11. **Selections.** The decision catalog (categories scoped living/garage/shared, items with recommendations) generates per-project selections. Admins add priced choices and approve one on the customer's behalf; variance against an allowance is computed.
12. **Reporting.** Budget variance across projects, hours per employee by range (CSV), and ordered/on-site/outstanding counts by project and category (CSV).

Data flows one way: controllers query Eloquent, hand-serialize arrays, and render Inertia pages; pages mutate via Inertia `router`/`useForm` posts that redirect back with a flash message. Shared props (`auth.user`, `flash`, lazily-evaluated `openTimeCard`) come from `HandleInertiaRequests`. The mobile API duplicates the same reads/writes as JSON.

### 1.6 Important business rules and invariants found in code

- One open time card per user; `clock-out` appends notes; a card open more than 10 hours gets one reminder email (stamped in `reminder_sent_at`).
- Document numbers: proposals and POs are per-year sequences computed under `lockForUpdate` and retried three times on unique-constraint collision; tasks are per-project sequences with the same pattern; change orders are per-project `max+1` **without** locking or retry (see §7).
- Proposals are immutable after draft; project deletion is blocked if any non-draft proposal exists so customer-facing numbers are never reissued. The same protection does **not** exist for sent POs or awarded bids (see §8).
- Budget writes on CO approval and bid award are guarded by `budget_line_id` to prevent double writes; reverting a CO deletes its line only if no money was recorded.
- Purchase order status transitions are the only thing that automatically sets takeoff `ordered`/`on_site`; crew can also toggle them manually.
- Schedule shifting never moves in-progress, done, or canceled jobs and stops traversal beneath them; predecessor must be on the same project; cycles are rejected.
- Punch-list sign-off requires at least one punch item and all punch items done.
- Photos: max 10 per log/task, JPEG/PNG/WebP/GIF up to 15 MB in, re-encoded; deleting a model deletes files via Eloquent hooks (DB cascades bypass hooks, so parents delete children through Eloquent first).
- Email opt-out is per user, enforced centrally in `Support\Notify`.
- Directory rows referenced by POs and bid responses keep a name snapshot so history survives deletion.
- Price book stores decimal dollars; proposals, budgets, POs, bids, selections, and leads store integer cents; conversion happens once in `TakeoffCosting::toCents`.

## 2. Project Architecture

### 2.1 Overall shape

This is a conventional Laravel monolith with Inertia rendering React pages server-side-routed, plus a thin Sanctum JSON API. The layering is: routes → controllers (validation + orchestration + serialization) → Eloquent models (relationships, casts, small domain helpers, status machines) → a `Support/` folder for the few pieces of real domain logic (formula evaluation, costing, schedule shifting, photo processing, notification recipients). There is no service or repository layer, no FormRequests beyond two auth ones, no Policies, and no API Resources.

For an app of this size and a team of one or two, that shape is appropriate. The debt is not "missing layers"; it is that the same logic now lives in two or three places because the web and API controllers were written by copy, and because several per-feature patterns (numbering, status transitions, photo storage, catalog generation, budget line writes) were re-implemented per feature instead of extracted once they recurred.

### 2.2 Backend

**Routing** (`routes/web.php`, `routes/api.php`): clear, grouped by module with comments; admin gating is done at the route level. Two oddities: the plain `/dashboard` route is an inline closure rendering a placeholder page, and the `/register` route from the starter kit remains public (§11).

**Controllers**: 27 web + 8 API controllers. Most are small and readable. The larger ones (`BidRequestController` 310 lines, `LeadController` 289, `JobController` 284, `PurchaseOrderController` 258, `TaskController` 226) each hold validation, business rules, and serialization together. This is fine at this size; the actual problems are the duplications listed in §13.

**Models**: thin and well-typed with docblocked relationships, `casts()`, constants for enums, and small domain methods (`varianceCents`, `endDate`, `canTransitionTo`, `editableBy`). Good. The status machines (`TRANSITIONS`, `canTransitionTo`) are copy-pasted into three models.

**Middleware**: `EnsureUserIsAdmin` and `HandleInertiaRequests` only. Shared props are minimal and the expensive one is lazy. Fine.

**Support classes**: `FormulaEvaluator` (safe recursive-descent parser, no `eval`), `TakeoffCosting`, `ScheduleShifter`, `Notify`, two near-identical photo storage classes, `TakeoffTemplate`. This is the right home for this logic; it should grow to absorb the duplicated pieces.

**Validation**: inline `$request->validate()` everywhere. Consistent, but duplicated verbatim between web and API controllers for trade partners, vendors, price items, rates, and time cards.

**Serialization**: hand-built arrays (`toRow`, `serialize`, `transform`). Explicit and safe (no accidental column leaks) except two places that pass whole models: `LeadController@pipeline/analytics/show` (full `Lead` models) and `DecisionCatalogController@index` (full category/item models). Not harmful today.

**Configuration**: standard Laravel. `config/inertia.php` is absent, so Inertia defaults apply (SSR "enabled" but no SSR server runs; harmless). Queue, cache, and session are on the database driver, which is appropriate for a small deployment. `.env` is untracked; `docs/` is gitignored on purpose (the repo is public), which means the three feature docs are not versioned with the code.

### 2.3 Frontend

**Structure**: `pages/` mirrors routes; `components/ui/` is shadcn; `components/buffalobuilt/` holds five app-specific shared components; `components/leads/` is the one feature that was split into components; `types/` has per-feature type files for about half the features; `lib/` has three utilities; `hooks/` are starter-kit hooks.

**Pages are the unit of work.** Most feature pages are single 300–730 line files containing the page plus two to seven inner components. `leads` is the exception and the model to follow.

**State**: Inertia props are the server state; local `useState`/`useForm` for UI. No store, and none is needed.

**Styling**: Tailwind 4 with design tokens; dark mode supported. Consistent visual language.

**Conventions are split**. Two form patterns (`useForm` versus `useState` + `router.post` + `usePage().props.errors`), two confirm patterns (`useConfirm` versus `window.confirm`), two URL patterns (`route()` versus hard-coded strings), two indentation widths (the leads feature and four pages use 2 spaces; prettier is configured for 4), two pagination UIs, and money/date helpers re-declared per page while `lib/money.ts` exists.

**Starter-kit residue**: `pages/welcome.tsx` (790 lines, no route), `app-header.tsx` (links to the Laravel starter-kit GitHub repo), `app-header-layout`, `nav-main`, `nav-footer`, `auth-card-layout`, `appearance-dropdown`, `coming-soon.tsx` (references a `docs/PLAN.md` that does not exist), `ui/alert`, `ui/collapsible`, `ui/toggle-group`, `ui/icon`, and `tests/Pest.php` (the suite is PHPUnit).

### 2.4 API architecture

The mobile API is a parallel set of controllers returning JSON for the same operations as the web. It is coherent (bearer tokens, abilities, admin middleware reused) but it is a copy, not a shared implementation. Any rule change in a web controller must be re-applied in the API controller by hand. There is also no versioning prefix and no rate limiting on login.

### 2.5 Database architecture

Well-designed relational schema with sensible cascade / null-on-delete choices, snapshot columns for history, composite indexes on the hot paths, and money in integer cents where it matters. Two structural concerns: foreign-key columns are not indexed on PostgreSQL (Laravel does not add FK indexes there, unlike MySQL), and LIKE searches are case-sensitive on PostgreSQL. Details in §8.

### 2.6 Where the architecture is tightly coupled or duplicated

- Web ↔ API controllers (validation, transforms, trade sync, per-page parsing): five feature pairs.
- Takeoff template seeding: `ProjectController@store`, `LeadController@convert`, `ProjectSeeder`.
- Photo pipeline: `DailyLogPhotoStorage` ≈ `TaskPhotoStorage`; `DailyLogPhotoController@stream` ≈ `TaskPhotoController@stream`.
- Numbering: `ProjectProposal::nextNumber` ≈ `PurchaseOrder::nextNumber`; `ProjectTask::nextNumber` and `ChangeOrderController@store` differ in safety.
- Status machines: `ProjectProposal`, `PurchaseOrder`, `BidRequest` plus three `transition()` actions.
- "Generate from catalog": `BudgetController@generate` ≈ `SelectionController@generate`.
- Budget line write on approval/award: `ChangeOrderController@decide` ≈ `BidRequestController@award`.
- `per_page` allowlist: 10 copies of the same three lines.

## 3. File-by-File Audit

Only files that need attention are listed. Files not listed were reviewed and are acceptable as-is.

### Backend

**`routes/auth.php`** — Public registration routes.
Wrong: `/register` creates a `crew` user for anyone who can reach the app. Employees are supposed to be created by admins (`EmployeeController`, seeder). Severity: **High** (security). Fix: remove the register routes and controller and the `register` page, or gate them behind an invite/`APP_ENV` check; update `RegistrationTest`. Split: no.

**`app/Http/Controllers/Api/AuthController.php`** — Token login.
Wrong: no rate limiting (the web login uses `RateLimiter` in `LoginRequest`; the API login has nothing), tokens never expire. Severity: **High**. Fix: add `throttle:5,1` (or a named limiter keyed on email+IP) to `POST /api/login`, set `sanctum.expiration`, and consider revoking older tokens for the same `device_name`.

**`app/Http/Controllers/ChangeOrderController.php`** — CO lifecycle.
Wrong: (a) `store` computes `max(number)+1` without lock or retry, unlike POs/proposals/tasks, so two simultaneous creates hit the unique index and 500. (b) `decide` does not check that the CO is pending, so an approved CO can be re-decided (the UI hides it, the endpoint allows it). (c) `decide` performs two writes (CO update, budget line create + CO update) with no transaction. (d) `revert` does not check status. Severity: **Medium** (correctness). Fix: add `nextNumber(projectId)` with `lockForUpdate` + `retry(3)` (mirror `ProjectTask`), guard `decide`/`revert` on status, wrap `decide` in `DB::transaction`, and move "write a budget line for X" into a shared `BudgetLineWriter` used by bids too.

**`app/Http/Controllers/ProjectController.php`** — Projects.
Wrong: (a) `store` creates the project and 13 lines without a transaction; (b) `destroy` blocks deletion only for non-draft proposals but cascades sent/received POs and awarded bid requests, freeing their numbers for reuse (the very problem the proposal guard solves); (c) `show` ships the entire price book (with category and vendor) as props on every project view. Severity: **Medium**. Fix: (a) transaction + extract `Project::seedStandardTakeoff()`; (b) extend the guard to non-draft POs and non-draft bid requests, or introduce soft deletes/archiving for projects; (c) send a lean `{id,name,unit,category,supplier_id}` list (already lean) but consider loading it lazily via a partial reload when the line dialog opens.

**`app/Http/Controllers/LeadController.php`** — CRM.
Wrong: `pipeline` and `analytics` return every lead with every column; analytics math runs client-side. `convert` duplicates template seeding. Severity: **Medium** (potential scale). Fix: exclude `lost`/`won` older than N months from the board by default or add a "show archived" toggle; compute analytics aggregates server-side; share the template seeding helper.

**`app/Http/Controllers/Admin/ReportController.php`** — Reports.
Wrong: (a) `timeSummaryRows` loads every time card in range into PHP and aggregates in a Collection (with `range=all` that is the whole table). (b) `range()` passes unvalidated `from`/`to` to `Carbon::parse`, which throws on garbage → 500. Severity: **Medium**. Fix: `selectRaw('user_id, count(*), sum(extract(epoch from clock_out_at - clock_in_at)/60)') groupBy user_id` (or the DB-agnostic `TIMESTAMPDIFF`/`julianday` equivalent) with `whereNotNull('clock_out_at')`; validate dates with `['nullable','date']`.

**`app/Http/Controllers/TimeCardController.php`** and **`Api/TimeCardController.php`** — Same unvalidated `Carbon::parse` on `from`/`to`; identical logic duplicated. Severity: **Medium**. Fix: one `TimeCardQuery`/`ClockService` used by both; validate dates.

**`app/Http/Controllers/JobController.php`** — Jobs.
Wrong: `calendar` `Carbon::createFromFormat('Y-m', ...)` throws on a malformed `month`; `jobOptions()` returns every non-canceled job in the system for the predecessor picker. Severity: **Medium** (potential scale, reliability). Fix: validate `month` with a regex rule; scope `jobOptions` to the selected project via a partial reload or an endpoint.

**`app/Http/Controllers/TradePartnerController.php`, `VendorController.php`, `PriceBookController.php`** and their `Api/` twins.
Wrong: full duplication (validation, transforms, `syncTrades`, `perPage`); `syncTrades` and `store` write without a transaction; LIKE search is case-sensitive on PostgreSQL. Severity: **Medium** (maintainability + a real search bug on the production DB). Fix: FormRequests (`TradePartnerRequest`, `VendorRequest`, `PriceItemRequest`), a `TradePartnerResource`-style transformer, `TradePartner::syncTrades()` in a transaction, and `whereRaw('LOWER(name) LIKE ?')`/`ilike` via a small `Builder` macro `whereLike`.

**`app/Http/Controllers/TaskController.php`** — Tasks.
Wrong: `syncChecklist` deletes and recreates rows on every edit outside the transaction, so checklist item ids change on every save (a stale page that toggles an old id gets a 404) and a failure mid-way loses the checklist. Severity: **Low–Medium**. Fix: upsert by position or id inside the transaction that creates/updates the task.

**`app/Http/Controllers/BidRequestController.php`** — Sub bidding.
Wrong: `storeResponse` does exists-check-then-create; a concurrent duplicate hits the unique index and 500s instead of the friendly flash. Also the largest controller. Severity: **Low**. Fix: catch `UniqueConstraintViolationException` (or `firstOrCreate`), and extract `award()` + section/line write into the shared `BudgetLineWriter`.

**`app/Http/Controllers/Settings/ProfileController.php`** — Self-service delete.
Wrong: any user, including the last admin, can permanently `forceDelete` their account; time cards cascade-delete (payroll history), daily logs and tasks become authorless. Severity: **Medium**. Fix: soft delete instead (consistent with admin deactivation), block if last admin, or remove self-delete for an internal tool.

**`app/Http/Controllers/PurchaseOrderController.php`** — POs.
Wrong: `itemRows` uses `abort(422, ...)` (HTML/JSON error, not a validation error the form can display). Severity: **Low**. Fix: throw `ValidationException::withMessages(['items' => ...])`.

**`app/Support/DailyLogPhotoStorage.php` / `TaskPhotoStorage.php`** — Photo processing.
Wrong: two copies of the same resize/encode/store routine; processing is synchronous in the request (up to 10 × 15 MB through GD). Severity: **Medium** (DRY, potential memory/time risk). Fix: one `PhotoProcessor::renditions(UploadedFile): {path, thumb_path, bytes}` used by both; consider a queued job for the web rendition when uploads grow, and set `upload_max_filesize`/`post_max_size`/`memory_limit` deliberately.

**`app/Models/ProjectProposal.php`, `PurchaseOrder.php`, `BidRequest.php`** — Status machines and numbering.
Wrong: identical `TRANSITIONS` + `canTransitionTo` and identical `nextNumber` implementations. Severity: **Low**. Fix: `HasStatusTransitions` trait and `HasYearlySequence` trait (prefix as a constant), and PHP backed enums for statuses (Laravel 12 enum casts).

**`app/Http/Middleware/HandleInertiaRequests.php`** — Shared props.
Wrong: computes an Inspiring quote on every request for a prop no app page uses. Severity: **Low**. Fix: remove `quote`.

**`bootstrap/app.php`** — Exception handling.
Wrong: `withExceptions` is empty; 403/404/419/500 render Laravel's HTML error page inside Inertia's error modal. Severity: **Medium** (reliability/UX). Fix: the standard Inertia handler: on 419 redirect back with a flash; on 403/404/500 in production render an `errors/error` Inertia page.

**`database/migrations/*`** — See §8 for missing PostgreSQL FK indexes and the three pairs of migrations sharing the same timestamp prefix.

**`tests/Pest.php`, `tests/Unit/ExampleTest.php`** — Dead. Delete.

- No caching layer beyond Inertia's `prefetch` on sidebar and nav links (used consistently). Fine.

## 7. API and Backend Audit

**Endpoint design.** RESTful, consistent naming, redirect-back with flash for web, JSON with `message` for API. Transition endpoints (`POST .../transition {status}`) are a clean pattern. Filters are sanitised (`status`, `trade`, `per_page`) in the newer controllers; older ones (`from`, `to`, `month`) are not (**confirmed 500s on malformed dates** in `ReportController`, `TimeCardController` ×2, `JobController@calendar`).

**Validation.** Present on every write. Gaps: `Api\LeadController` trusts a client-supplied `createdAt` for `submitted_at` and does not cap `email` length; `Api\AuthController` has no throttle; `PurchaseOrderController@itemRows` uses `abort(422)` instead of a validation exception.

**Authorization.** Role gating is correct and tested (crew 403 tests exist for every admin module). Object-level checks exist where ownership matters (logs, tasks, jobs). Deliberately permissive spots worth documenting: any user can toggle any takeoff line, view any photo, create tasks on any project, and view any project's takeoff with costs. `ProfileController@destroy` is the one authorization gap (last admin can delete self).

**Queries.** Eager loading is used correctly everywhere I traced (`with(...)`, `withCount`, `load`); I found no N+1 in page renders. `HandleInertiaRequests` runs one indexed query per full page load. Remaining inefficiencies: PHP-side aggregation in reports and `BudgetController@report`; PHP-side sorting in `BudgetController@index/export`, `SelectionController@index`, `ProjectPhotoController@index` (each could be an `orderBy` on a join); repeated `TradePartner::distinct()->pluck('location')` on every directory request (cheap).

**Transactions.** Used in proposals, POs, bids, tasks, lead conversion, schedule shifting. Missing where multiple rows are written: `ProjectController@store` (project + 13 lines), `ChangeOrderController@decide` (CO + line), `TradePartnerController@store/update` (partner + trades), `TaskController@store/update` (checklist outside the transaction), `SelectionController@destroyChoice` (delete + approval reset), `BudgetController@generate` / `SelectionController@generate` (N inserts).

**Concurrency.** Numbering for proposals/POs/tasks is handled with lock + retry. Change orders are not. `BidRequestController@storeResponse` and `ProjectController@store` (`Rule::unique('projects','name')` without a DB unique index) can still race.

**Caching.** Nothing is cached and nothing needs to be at this scale. Cheap wins later: the price book option list and `TradePartner::TRADES`-style reference lists could be cached per request in a shared prop.

**Bottleneck candidates (ordered):** time-summary report with `range=all`; CRM kanban/analytics payload; calendar `jobOptions`; project page price-book payload; directory search per keystroke; synchronous image processing on upload.

**API consistency.** The API returns `isAdmin`, `filters`, and option lists in list responses, mirroring the Inertia props, which is pragmatic for the mobile client. There is no `/api/v1` prefix and no API tests (only `POST /api/leads` is covered via the notification test).

**Relationships and constraints:** correct and thoughtful. Cascade on true children (lines, items, photos, responses), `nullOnDelete` on references that should survive (users, vendors, partners, budget lines), unique constraints where business rules require them (`(project_id, number)` for COs and tasks, `(bid_request_id, trade_partner_id)`, `(project_id, decision_item_id)`, `(project_id, budget_line_definition_id)`, `(name, scope)` for decision categories). The circular FK between `bid_requests.awarded_response_id` and `bid_responses` is added after both tables exist — correct.

**Indexes present:** `time_cards (user_id, clock_out_at)`, `(clock_in_at)`; `project_jobs (scheduled_date)`, `(project_id, scheduled_date)`; `takeoff_lines (project_id, sort)`; `daily_logs (project_id, log_date)`; `leads (status)`; `(project_id, status)` on proposals, POs, bids, tasks; `users (role)`; `decision_categories (scope)`; vendors/partners `location`, `type`, `used_before`; `trade_partner_trades (trade)`.

**Confirmed gap: FK columns unindexed on PostgreSQL.** Laravel's `foreignId()->constrained()` creates only the constraint; PostgreSQL does not auto-index FK columns (MySQL does), and the local/production database is PostgreSQL. Columns used in joins, `whereHas`, `whereIn`, or as the second column of a unique index only (so unusable for lookups on that column alone):

`takeoff_lines.price_item_id`, `takeoff_lines.supplier_id`, `project_job_user.user_id` (drives `$user->jobs()`), `daily_logs.user_id`, `daily_log_photos.daily_log_id` (drives the gallery `whereHas`), `lead_activities.lead_id`, `leads.assigned_to_user_id`, `leads.converted_project_id`, `project_selections.decision_item_id`, `selection_choices.project_selection_id`, `project_budget_lines.budget_section_id`, `project_budget_lines.budget_line_definition_id`, `change_orders.budget_line_id`, `purchase_order_items.purchase_order_id`, `purchase_order_items.takeoff_line_id`, `bid_requests.budget_line_id`, `bid_responses.trade_partner_id`, `project_tasks.assigned_to_user_id`, `project_jobs.predecessor_job_id`, `task_checklist_items.project_task_id`, `task_photos.project_task_id`, `price_items.preferred_vendor_id`.

Add one migration with `$table->index(...)` for each. At current volumes this is invisible; at thousands of rows the sequential scans on cascade deletes and `whereHas` will show.

**Confirmed: case-sensitive search.** `where('name', 'like', "%x%")` is case-sensitive on PostgreSQL. Tests pass because SQLite's LIKE is case-insensitive. Fix with `ilike` (PG-only) or `LOWER(col) LIKE LOWER(?)` via a `Builder::macro('whereLike')`.

**Data types:** money in `bigInteger` cents where it matters, `decimal(12,2)` for the price book and dimensions, `decimal(5,2)` for waste. Statuses are strings with app-level constant lists (no DB `CHECK`), which is acceptable; PHP backed enums would tighten it. `takeoff_lines.formula` is `string(255)`, fine.

**Normalisation:** appropriate. Deliberate denormalisation (`vendor_name`, `trade_partner_name`, `project_budget_lines.name` copied from definition, proposal line snapshots) is documented and correct for history. `trade_partner_trades` as a child table with a fixed vocabulary is fine.

**Duplicate or missing data-model links (business gaps, not bugs):** `time_cards` has no `project_id`, so labor actuals in the budget cannot be derived from hours; daily logs have free-text `crew_present` instead of a pivot to users; `projects.name` uniqueness is validation-only (no DB unique index).

**Migrations:** three pairs share a timestamp prefix (`2026_08_17_000001_*`, `2026_08_18_000001_*`, `2026_08_19_000001_*`); ordering falls back to filename sort, which currently works but is fragile. No `database/schema` dump; migrations are the source of truth, fine.

## 11. Security Audit

Confirmed findings, highest first:

1. **Public self-registration** (`routes/auth.php`, `RegisteredUserController`): anyone can create a crew account and read the price book, projects with cost estimates, trade partner negotiated prices, calendar, daily logs, and upload photos/tasks. High.
2. **No rate limiting on `POST /api/login`** (`Api\AuthController`): credential stuffing against employee emails is unthrottled. High. Also no throttle on `POST /api/leads` (token-protected, but the token lives in a public website's deploy; if leaked, unbounded lead spam triggers admin emails). Medium.
3. **Non-expiring Sanctum tokens** (`sanctum.expiration = null`), no revocation UI, and deactivated (soft-deleted) users' tokens are only blocked because the global scope hides the user; reactivation restores old tokens. Medium.
4. **Self-service permanent account deletion** (`ProfileController@destroy`) with no last-admin guard and cascade of payroll time cards. Medium.
5. **Production cookie flags** rely on env: `SESSION_SECURE_COOKIE` is unset in `.env.example`. Ensure it is `true` behind HTTPS. Low (deployment).
6. **File uploads:** validated by `image` + `mimes` + size, re-encoded through GD (good, strips payloads), stored on the private disk, streamed via auth routes with `Cache-Control: private`. Remaining risk is resource exhaustion from large batches (Medium potential), not content.
7. **XSS:** React escaping everywhere; the only `dangerouslySetInnerHTML` renders Laravel's paginator labels (server-controlled). PDFs use Blade `{{ }}` escaping. Low.
8. **CSRF:** Inertia/axios XSRF for web; bearer tokens for API. OK.
9. **SQL injection:** all queries go through the query builder with bindings, including LIKE searches. OK.
10. **Mass assignment:** `$fillable` is explicit on every model; controllers pass validated arrays. `LeadController@update` fills validated data only. OK.
11. **Authorization bypass:** none found. Role checks are server-side; `isAdmin` props are for UI only and every admin route is middleware-gated. Object-level checks exist where ownership matters. The `decide`/`revert` status guards missing on change orders are integrity issues, not privilege escalation.
12. **Sensitive data exposure:** `User` hides password and remember token; API `userPayload` is explicit. Lead PII is visible to all crew on `/leads` (by design). The seeder prints a website integration token to the console (fine for local; ensure production tokens are rotated).
13. **Secrets:** `.env` untracked; no secrets in code. The local `.env` has a trivial Postgres password, which is expected for local.
14. **Error messages:** `APP_DEBUG=true` in `.env.example`; make sure production sets `false` (default Laravel behaviour).

## 15. Testing

**Current state:** 33 feature test classes, 260 test methods, PHPUnit, SQLite in-memory, CI on push/PR (`tests.yml`). Coverage is strong for a project this size: every module has permission tests (crew 403), lifecycle tests (status matrices, numbering, cascade rules), and business-rule tests (waste math, immutable proposals, budget writes on award/approval, schedule shifting, photo limits, notification recipients). Unit tests: `FormulaEvaluatorTest` only.

**Gaps (ordered by risk):**
1. **Mobile API** — zero tests for `POST /api/login`, `/api/user`, `/api/time-card/*`, `/api/price-book`, `/api/trade-partners`, `/api/vendors`, `/api/admin/*`. The mobile app depends on these and they are hand-copied from the web controllers.
2. **PostgreSQL behaviour** — CI runs SQLite; `lockForUpdate`, unique-with-NULL semantics, LIKE case sensitivity, and `FOR UPDATE` + aggregates (a migration comment mentions this) are untested on the production engine. Add a Postgres service to `tests.yml`.
3. **Change order concurrency and status guards** — no test that `decide` on a non-pending CO is rejected (because it is not).
4. **Project deletion guards** for POs/bids — none (because they do not exist).
5. **`TakeoffCosting` unit tests** — costing is tested indirectly through pages; a direct unit test with edge cases (null price, zero qty, waste rounding) is cheap.
6. **Frontend** — no unit tests (`lib/formula.ts` should share golden cases with the PHP evaluator to keep the two parsers in lockstep), no component tests, no E2E.
7. **Reports** with `range=all` and malformed dates.

**Recommended order:** API feature tests → Postgres in CI → CO guards/numbering → Vitest for `formula.ts` and `money.ts` → Playwright smoke (login, clock in/out, create project → enter dimensions → new proposal → download PDF, kanban drag).

**Testability:** controllers are thin enough to test through HTTP; the duplicated logic is the main testability cost (each fix needs two tests). Extracting the services in §13 lets one unit test cover both surfaces.

## 18. Final Action Plan

### Immediate (this week)

1. **Close registration.** Remove the `register` routes/controller/page (or gate behind an admin-issued invite). Why: any visitor can create an account that reads cost data.
2. **Throttle and expire API auth.** Add `throttle` to `POST /api/login` and `POST /api/leads`; set `sanctum.expiration`; delete a user's tokens on deactivation. Why: unbounded credential guessing and lead spam.
3. **Change order integrity.** Lock+retry numbering, status guards on `decide`/`revert`, transaction around decide. Why: duplicate numbers and re-decided approvals corrupt contract records.
4. **Project delete guard.** Block deletion when non-draft POs or non-draft bid requests exist (same reasoning as proposals). Why: reissued supplier/customer document numbers.
5. **Validate date/month query params** in reports, time cards (web + API), calendar. Why: trivial 500s.
6. **Inertia exception handler + error page.** Why: every 403/404/419 today is an ugly modal.
7. **Case-insensitive search** via a `whereLike` macro. Why: search is broken on the production database.
8. **`onError` toasts on inline saves** (budget, selections, bids, task toggles). Why: silent data loss from the user's point of view.

### Short-term (next 2–4 sweeps)

1. **Postgres FK index migration** (~22 indexes) and **Postgres service in CI**.
2. **API tests** for every `/api` route, then **extract shared FormRequests/transformers/`TimeCardService`** so web and API share one implementation.
3. **SQL aggregation** for the time-summary report; bound the kanban/analytics payload and move analytics math server-side; scope the calendar predecessor picker.
4. **Debounced `SearchInput`**, `MoneyInput`, `PageHeader`, `DataTable`, `StatCard`, `StatusBadge`, `PhotoLightbox`, `useEntityDialog`; consolidate `lib/money.ts` and `lib/dates.ts`; replace `window.confirm`; use `route()` everywhere.
5. **Split the ten large pages** into `components/<feature>/` following the leads layout, one page per sweep as they are touched.
6. **Delete dead starter code** and unused Radix packages; move tooling to devDependencies; strip the BOM; make CI run `prettier --check` and `pint --test`.
7. **Photo pipeline:** one `PhotoProcessor`; document PHP upload/memory limits; decide whether to queue renditions.
8. **Self-delete:** soft delete + last-admin guard, matching admin deactivation.
9. **Task checklist upsert** inside the transaction.
10. **Real dashboard** (or role-based redirect) so the first screen is useful.

### Long-term (plan and schedule)

1. **Traits/enums for statuses and numbering** across proposals, POs, bids, tasks, COs; a `BudgetLineWriter` for all "write committed cost to budget" flows. Why: the next document type (invoices, sub contracts) should not copy a fourth state machine.
2. **Project archiving / soft deletes** instead of hard cascades. Why: projects accumulate legally relevant documents.
3. **Link time cards to projects** (optional `project_id`, or a job link) so labor actuals can flow into the budget the way sub bids and POs already do. Why: closes the biggest gap in bid-vs-actual.
4. **Frontend test foundation:** Vitest with shared golden cases for the formula parser, component tests for `MoneyInput`/`Pagination`, Playwright smoke on the estimate → proposal → PDF path.
5. **Queue/scheduler observability** (failed-job alerts, `schedule:run` health) since email delivery depends on both.
6. **API versioning** (`/api/v1`) before the mobile app ships widely, so the shared-implementation refactor can change payloads safely.
7. **Version the docs.** `docs/` is gitignored because the repo is public; move sensitive figures out and keep the three feature docs (proposals, notifications, sub bidding) in the repo, or move the repo private. Why: the docs are the best onboarding material this project has and they are currently only on one machine.
